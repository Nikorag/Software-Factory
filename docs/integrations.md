# Integrations
Verified so far: gh (authenticated), Claude Code 2.1.x CLI. SpecKit commands (from its README): `specify init`, `/speckit-constitution`, `-specify`, `-plan`, `-tasks`, `-implement`, `-converge`; re-verify against the installed version in Milestone 6. Linear, Bionic: pending.

## Git and repositories (Milestone 3)
- All git calls go through `src/repo/git.ts`: no shell, no credential prompts, and a guard (`assertSafeGitArgs`) that rejects force/mirror/delete pushes, pushes to protected branches (the project's default branch), and deletion of protected branches. A push must name an explicit branch.
- `factory project:validate [id]` inspects each enrolled repo **read-only**: git status, default branch, origin (credentials stripped), CLAUDE.md, `.specify/`, submodules, build system and candidate test/lint/typecheck commands, GitHub Actions workflows, branch protection. Existing config is never overwritten; detected commands are suggestions.
- Branch protection is read with `gh api`. A 404 on the branch is only trusted as "unprotected" after the repository itself is confirmed visible; otherwise the result is `unknown`. **Full autonomy errors on unprotected branches or protection with no required checks, and warns when unverifiable.** Milestone 8 must refuse to auto-merge unless protection was actually verified.
- SSH host aliases such as `git@github.com-<account>:owner/repo.git` (multi-account setups) are recognised. `gh` uses its *active* account, so a repo owned by the other account reads as inaccessible until you `gh auth switch`. Set `github: { account: <login> }` per project: `gh` then runs as that account for that call only (token read from gh's keyring into the child process environment; never stored or logged; the global active login is never switched). A configured account with no gh login fails loudly rather than falling back to another account.

## Linear (Milestone 4)
Verified against Linear's published GraphQL schema (`linear/linear` repo, `packages/sdk/src/schema.graphql`): `issues(filter)` with `team.key`, `state.name`, `labels.some.name`, `project.id`; `issueUpdate` with `stateId` / `addedLabelIds` / `removedLabelIds`; `commentCreate` with a client-supplied `id`; `attachmentLinkGitHubPR`.
- **Auth:** personal API key from the env var named by `apiKeyEnv` (default `LINEAR_API_KEY`), sent as the raw `Authorization` header (no `Bearer`). Never stored in config or logged.
- **Config:** `config/linear.yaml` holds status and label *names* (not ids). Ids are resolved per team at send time. `pnpm factory linear:check` (read-only) verifies the key and reports any configured status or label missing from each bound team. The factory never creates statuses or labels; create them in Linear first.
- **Binding:** a project opts in with `linear: { teamKey, projectId? }` in `config/projects.yaml`. The most specific binding wins (team+project beats team-only); equal bindings are reported as ambiguous and skipped.
- **Eligibility** (`src/linear/eligibility.ts`): label `factory:enabled`, status "Ready for specification", no `factory:blocked`, project enabled and *validated*, no earlier job for the issue (finished or failed jobs are never silently re-run; cancelled ones can be re-queued). `factory:bugfix|feature|maintenance` pick the workflow (default `feature`). A job is `autonomous` only if the issue has `factory:autonomous` **and** the project is `autonomy: full`.
- **Polling:** `pnpm factory linear:discover [--dry-run]`. Idempotent; a failure in one project does not stop the others. Webhooks can later feed the same `discoverIssues` path.
- **Writes go through a durable outbox** (`linear_outbox`). The row is created in the same transaction as the stage change. `linear:flush` sends them in order per issue, with retry and backoff (transient) or `failed` (permanent, recorded in `decisions`). Consecutive status changes are coalesced to the latest. Comments carry a deterministic id and a hidden marker, so a retry after an ambiguous failure cannot duplicate them. Linear outages therefore never lose or reorder updates, and never block job execution.
- **Status mapping** (`src/linear/reporter.ts`): requirements/spec stages → Specification review; implementation through final validation → In progress; PR/CI/merge validation → Ready for review; merging → Merging; completed → Done; blocked/needs-attention/failed → Blocked plus the `factory:blocked` label and a comment with the reason. Retrying removes the label.
- **Dry run:** nothing is queued; each intended write is recorded in `decisions`.
- Not yet wired: PR linking (`link_pr` op exists; Milestone 8 enqueues it) and running discovery/flush on a timer inside `serve` (Milestone 9 scheduler).

## Multi-repo binding (JAM team)
Each Linear project maps to its own repository: `linear: { teamKey: JAM, projectName: <Linear project> }` plus `repository:` and `github.account`. `loadConfig` rejects two entries bound to the same Linear target or the same repository path. A team-wide entry (no `projectName`) acts only as a fallback for issues with no more specific binding.

## GitHub plan limits (important)
On a free GitHub plan, **private repositories cannot use branch protection or rulesets** (the API answers 403 "Upgrade to GitHub Pro or make this repository public"). The factory reports this as `protection: unavailable` (distinct from `unprotected` and `unknown`). Such a project can run in `supervised` mode, but `autonomy: full` will not auto-merge until one of: upgrade the plan, make the repo public, or an explicit decision to accept factory-side enforcement of required checks (not implemented; would be recorded as an ADR).

## Claude Code (Milestone 5)
Verified by running the installed CLI (2.1.332), not assumed. Adapter: `src/agents/claude.ts`.
- **Invocation:** `claude -p --output-format json --permission-mode dontAsk --setting-sources "" --strict-mcp-config --tools … --allowedTools … --disallowedTools …`, prompt on **stdin** (never argv), cwd = the job worktree. Result JSON provides `result`, `structured_output` (with `--json-schema`), `session_id`, `total_cost_usd`, `usage`, `num_turns`, `permission_denials`, `is_error`, `api_error_status`. All of it is recorded in `agent_invocations`.
- **Auth and cost:** the normal subscription login (`claude auth status` reports `authMethod: claude.ai`). The `total_cost_usd` in the CLI output is a *list-price estimate* (`costBasis: "list"`), not a charge; it is stored as `estimatedListCostUsd` and is useful only as a relative measure. The real constraint is the subscription's usage limit, shared with interactive use. `--bare` is deliberately *not* used: it never reads OAuth/keychain. The child environment is an allowlist (`src/agents/env.ts`), so `ANTHROPIC_API_KEY` (which would switch to metered billing), `GH_TOKEN`, `LINEAR_API_KEY`, cloud credentials and `SSH_AUTH_SOCK` never reach an agent.
- **Settings isolation:** `--setting-sources ""` ignores user/project settings files, so permissions are defined by the factory, not by a repository an attacker may control. Role prompts come from this repo's `agents/*.md`, not from the target repo.
- **Process control:** the child runs in its own process group; timeout and cancellation (SIGTERM, then SIGKILL after a grace period) kill the whole tree. Output is captured to a per-invocation log under `<dataDir>/logs/agents/`.
- **Failure classes:** `auth`, `rate_limited` (subscription limits), `transient`, `timeout`, `cancelled`, `invalid_output`, `error`. Transient ones are retryable by the engine; auth and invalid output are not.
- **Resuming:** implementer sessions are persisted (`--resume <session_id>` for remediation); reviewers use `--no-session-persistence`.

### Permission model (each rule verified with real calls; see `tests/live/`)
Run `FACTORY_LIVE=1 pnpm vitest run tests/live` to re-verify against an upgraded CLI (uses a little subscription quota).
- A **deny beats a broad allow**. Path scoping uses `Edit(<glob>)`, which governs both the Edit and Write tools. (`Write(<glob>)` does not work.) Bare `Write`/`Edit` allows are what enable those tools.
- `Bash(git:*)` allowed with `Bash(git push:*)` denied permits other git commands and refuses push.
- **Never grant bare `Read`/`Grep`/`Glob`.** With no rule they are confined to the worktree; a bare allow lets an agent read any file the user can. (A live test caught this mistake; there is a regression test.) Bash built-ins such as `cat`/`ls`/`grep` are also refused outside the worktree.
- **Never grant bare `Write`/`Edit`.** They allow writing anywhere the user can (found live: an implementer wrote to `$HOME` and a sibling directory). The implementer's edit access is `Edit(//<worktree>/**)` only; verified live for the Write tool, shell redirection and `cp` (`tests/live`).
- **Path rules must be absolute.** Claude Code's shell keeps `cd` between calls and relative rules resolve against the *current* directory, so after `cd specs/x` the rule `Edit(specs/**)` silently matched nothing and the agent's in-scope edits were refused (found live: it stalled spec remediation; reproduced 4/4, and the live test `cd drift` fails without the fix). Every scoped allow and every protected-path deny is therefore emitted in relative **and** absolute (`//abs/path/...`) form, for both spellings of the root on macOS (`/var` and `/private/var` are not equated). Agents are also told never to `cd`. Protected-path denies held under drift even before this fix; they are anchored anyway.
- Profiles (`src/agents/permissions.ts`): `read-only` (reviewers/analysts/classifier), `spec-writer` (may only edit `specs/**` and `.specify/**`), `implementer` (edit + `git add/commit` + the project's test/lint commands; denied: push, fetch, pull, checkout/switch/branch/reset, config, remote, worktree, `gh`, curl/wget/ssh/scp, sudo, `rm -rf`, publish, docker, and edits to every protected path). A role maps to exactly one profile (`src/agents/roles.ts`); there is no per-call override.
- **Independent verification** (`AgentRunner`): after every run the factory checks the worktree itself. Any change (committed, staged, modified, untracked or renamed-away) matching `protectedPaths` fails the run and records an `agent.violation` decision; a read-only agent that altered the worktree fails the same way. Correctness does not depend on Claude Code's permission system alone.

## Spec Kit (Milestone 6)
Verified against github/spec-kit docs and the installed CLI (`specify` 1.4.4, installed with `uv tool install specify-cli`); nothing here is invented.
- **Setup:** `specify init --here --force --integration claude --script sh --non-interactive --ignore-agent-tools`. It adds only `.claude/skills/speckit-*/` and `.specify/` (scripts, templates, memory, workflow); application code is untouched. The factory runs this itself, never an agent.
- **Flow:** `constitution` (once per project) → `specify` → `clarify` → `plan` → `tasks` → `analyze` (read-only) → `implement` → `converge`. Artefacts land in `specs/<dir>/` (`spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, `tasks.md`, `checklists/requirements.md`) plus `.specify/feature.json`.
- **Branching:** Spec Kit's branch creation is an optional `git` extension, not installed. The factory owns branches (`factory/<KEY>`); `SPECIFY_FEATURE_DIRECTORY` is pinned per ticket to `specs/<key>-<slug>` so concurrent worktrees never race on Spec Kit's number scanning.
- **Why the factory drives the skills itself instead of `specify workflow run`:** Spec Kit's own workflow steps call `claude -p` without the factory's permission profile. Each skill is run through `ClaudeCodeAgent` under the `spec-writer` profile. We do not reimplement Spec Kit: the agent is told to read and follow the repository's own `.claude/skills/speckit-<step>/SKILL.md` (skills are not auto-registered because `--setting-sources ""` ignores repo settings on purpose; verified live that this works).
- **Clarify is interactive in Spec Kit.** In an automated run the prompt tells the agent to answer its own questions from the ticket, codebase and constitution and mark each as an "agent decision" in the artefact; anything that truly needs a human goes under `## Open questions requiring a human`, which blocks the job and is posted to Linear.
- **Protected:** agents cannot edit `.claude/**`, `.specify/scripts|templates|workflows|integrations/**`. The spec-writer may edit only `specs/**`, `.specify/memory/**`, `.specify/feature.json`, and may run Spec Kit's four helper scripts.

## Specification stages (how the factory uses Spec Kit)
| Stage | What happens |
|---|---|
| `DISCOVERED` / `ELIGIBILITY_CHECK` | Re-reads the live ticket; stops if it lost `factory:enabled`, gained `factory:blocked`, or moved status since discovery. |
| `REQUIREMENTS_ANALYSIS` | Creates the job worktree. Cheap advisory classification (Haiku). Claude read-only analyst answers `ready` or `needs_clarification` with exact questions; the latter blocks the job and posts them to Linear. |
| `SPECIFICATION_GENERATION` | Writes `ticket.md`, then runs `specify → clarify → plan → tasks`. After each step the **factory** commits the artefacts (`spec(KEY): <step>`, author "Software Factory") and checkpoints it, so a crash or retry resumes at the failed step. Blocks with onboarding instructions if Spec Kit is not on the default branch. |
| `SPECIFICATION_REVIEW` | Independent review of the full artefact text by the `independent_review` route (Haiku by default: a different model from the author; read-only profile). Only if that route is a *local* model and it is unavailable: fall back to a fresh Claude reviewer (`independentReviewFallback: claude`, recorded as `review.degraded`) or block. `blocker`/`major` findings → remediation. |
| `SPECIFICATION_REMEDIATION` | Claude spec-writer fixes valid findings and must reject invalid ones with evidence (stored as `remediation.rejected` decisions). Minor findings are not sent. |
| `SPECIFICATION_VALIDATION` | Deterministic gate calibrated on real output (files present; FR-/SC- ids; Given/When/Then; tasks; checklist complete; no `[NEEDS CLARIFICATION]` or template placeholders; no open human questions) then Spec Kit `analyze` (read-only, structured). CRITICAL/HIGH findings → remediation. |
Remediation is capped at `maxRemediationAttempts` (3), then `NEEDS_ATTENTION`. Note the workflow is review → remediation → validation (as specified); the reviewer does not re-review after a fix, validation and analyze re-check consistency.

## Onboarding a project
`pnpm factory project:onboard <id>` creates the local branch `factory/onboard-speckit` in `<dataDir>/workspaces/<id>/_onboard-speckit`: `specify init` (committed), then an agent writes an *evidence-based* constitution from the README, CLAUDE.md, CI and tooling (committed). It never pushes, never overwrites an existing `.specify/`, and is idempotent and crash-safe. The constitution is project policy, so a human reviews and merges it (PR creation arrives in Milestone 8); until then `SPECIFICATION_GENERATION` blocks with exactly this instruction.

## Linear workspace setup
`pnpm factory linear:check` (read-only) lists what is missing per bound team, split into **required** (what the factory writes today: statuses Ready for specification, Specification review, In progress, Ready for review, Merging, Done, Blocked; labels `factory:enabled`, `factory:blocked`) and **optional** (`Ready for development`, `Changes requested`, and the `factory:autonomous|bugfix|feature|maintenance` labels). `pnpm factory linear:setup` creates the missing required items as a **dry run by default**; `--apply` creates them, `--include-optional` adds the rest. It only creates (team-scoped labels, sensible state types), never edits or deletes, matches existing names case-insensitively, and is idempotent. Verified against the real `JAM` team.
