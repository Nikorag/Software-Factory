# Integrations
Verified so far: gh (authenticated), Claude Code 2.1.x CLI. Spec Kit commands (from its README, used only in the `speckit` planning mode): `specify init`, `/speckit-constitution`, `-specify`, `-plan`, `-tasks`, `-implement`, `-converge`; re-verify against the installed version in the pipeline. Other trackers and Bitbucket have their own pages: [trackers](trackers.md), [Jira](jira.md), [GitHub Issues](github-issues.md), [Bitbucket](bitbucket.md).

## Git and repositories
- All git calls go through `src/repo/git.ts`: no shell, no credential prompts, and a guard (`assertSafeGitArgs`) that rejects force/mirror/delete pushes, pushes to protected branches (the project's default branch), and deletion of protected branches. A push must name an explicit branch.
- `factory project:validate [id]` inspects each enrolled repo **read-only**: git status, default branch, origin (credentials stripped), CLAUDE.md, `.specify/`, submodules, build system and candidate test/lint/typecheck commands, GitHub Actions workflows, branch protection. Existing config is never overwritten; detected commands are suggestions.
- Branch protection is read with `gh api`. A 404 on the branch is only trusted as "unprotected" after the repository itself is confirmed visible; otherwise the result is `unknown`. **Full autonomy errors on unprotected branches or protection with no required checks, and warns when unverifiable.** (Delivery is PR-only, so nothing is ever auto-merged; the rule keeps `autonomy: full` honest about the safety net a human merge relies on.)
- SSH host aliases such as `git@github.com-<account>:owner/repo.git` (multi-account setups) are recognised. `gh` uses its *active* account, so a repo owned by the other account reads as inaccessible until you `gh auth switch`. Set `github: { account: <login> }` per project: `gh` then runs as that account for that call only (token read from gh's keyring into the child process environment; never stored or logged; the global active login is never switched). A configured account with no gh login fails loudly rather than falling back to another account.

## Linear
One of three tracker kinds (Linear, Jira, GitHub Issues); a profile can hold several connections and each project picks one (see [trackers](trackers.md)). The details below are Linear's. Verified against Linear's published GraphQL schema (`linear/linear` repo, `packages/sdk/src/schema.graphql`): `issues(filter)` with `team.key`, `state.name`, `labels.some.name`, `project.id`; `issueUpdate` with `stateId` / `addedLabelIds` / `removedLabelIds`; `commentCreate` with a client-supplied `id`; `attachmentLinkGitHubPR`.
- **Auth:** personal API key from the env var named by `apiKeyEnv` (default `LINEAR_API_KEY`), sent as the raw `Authorization` header (no `Bearer`). Never stored in config or logged.
- **Config:** `config/linear.yaml` holds status and label *names* (not ids). Ids are resolved per team at send time. `pnpm factory linear:check` (read-only) verifies the key and reports any configured status or label missing from each bound team. The factory never creates statuses or labels; create them in Linear first.
- **Binding:** a project opts in with `linear: { teamKey, projectId? }` in `config/projects.yaml`. The most specific binding wins (team+project beats team-only); equal bindings are reported as ambiguous and skipped.
- **Eligibility** (`src/linear/eligibility.ts`): label `factory:enabled`, status "Ready for specification", no `factory:blocked`, project enabled and *validated*, no earlier job for the issue (finished or failed jobs are never silently re-run; cancelled ones can be re-queued). `factory:bugfix|feature|maintenance` pick the workflow (default `feature`). A job is `autonomous` only if the issue has `factory:autonomous` **and** the project is `autonomy: full`.
- **Polling:** `pnpm factory linear:discover [--dry-run]`. Idempotent; a failure in one project does not stop the others. Webhooks can later feed the same `discoverIssues` path.
- **Writes go through a durable outbox** (`linear_outbox`). The row is created in the same transaction as the stage change. `linear:flush` sends them in order per issue, with retry and backoff (transient) or `failed` (permanent, recorded in `decisions`). Consecutive status changes are coalesced to the latest. Comments carry a deterministic id and a hidden marker, so a retry after an ambiguous failure cannot duplicate them. Linear outages therefore never lose or reorder updates, and never block job execution.
- **Status mapping** (`src/linear/reporter.ts`): requirements/spec stages → Specification review (in `haiku_prompt` mode requirements go straight to In progress, there is no specification phase); implementation through final validation, and merge-conflict resolution → In progress; PR/CI/merge validation → Ready for review; merging → Merging; completed → Done; blocked/needs-attention/failed → Blocked plus the `factory:blocked` label and a comment with the reason. Retrying removes the label.
- **Dry run:** nothing is queued; each intended write is recorded in `decisions`.
- PR links are written back to the ticket by the delivery stages, and discovery and the write-back flush run on a timer inside `serve`.

## Multi-repo binding (JAM team)
Each Linear project maps to its own repository: `linear: { teamKey: JAM, projectName: <Linear project> }` plus `repository:` and `github.account`. `loadConfig` rejects two entries bound to the same Linear target or the same repository path. A team-wide entry (no `projectName`) acts only as a fallback for issues with no more specific binding.

## GitHub plan limits (important)
On a free GitHub plan, **private repositories cannot use branch protection or rulesets** (the API answers 403 "Upgrade to GitHub Pro or make this repository public"). The factory reports this as `protection: unavailable` (distinct from `unprotected` and `unknown`). Such a project can run in `supervised` mode, but `autonomy: full` is refused until one of: upgrade the plan, make the repo public, or an explicit decision to accept factory-side enforcement of required checks (not implemented; would be recorded as an ADR). The factory never merges either way.

## Claude Code
Verified by running the installed CLI (2.1.332), not assumed. Adapter: `src/agents/claude.ts`.
- **Invocation:** `claude -p --output-format json --permission-mode dontAsk --setting-sources "" --strict-mcp-config --tools … --allowedTools … --disallowedTools …`, prompt on **stdin** (never argv), cwd = the job worktree. Result JSON provides `result`, `structured_output` (with `--json-schema`), `session_id`, `total_cost_usd`, `usage`, `num_turns`, `permission_denials`, `is_error`, `api_error_status`. All of it is recorded in `agent_invocations`.
- **Auth and cost:** the normal subscription login (`claude auth status` reports `authMethod: claude.ai`). The `total_cost_usd` in the CLI output is a *list-price estimate* (`costBasis: "list"`), not a charge; it is stored as `estimatedListCostUsd` and is useful only as a relative measure. The real constraint is the subscription's usage limit, shared with interactive use. `--bare` is deliberately *not* used: it never reads OAuth/keychain. The child environment is an allowlist (`src/agents/env.ts`), so `ANTHROPIC_API_KEY` (which would switch to metered billing), `GH_TOKEN`, `LINEAR_API_KEY`, cloud credentials and `SSH_AUTH_SOCK` never reach an agent.
- **Settings isolation:** `--setting-sources ""` ignores user/project settings files, so permissions are defined by the factory, not by a repository an attacker may control. Role prompts come from this repo's `agents/*.md`, not from the target repo.
- **Process control:** the child runs in its own process group; timeout and cancellation (SIGTERM, then SIGKILL after a grace period) kill the whole tree. Output is captured to a per-invocation log under `<dataDir>/logs/agents/`.
- **Failure classes:** `auth`, `rate_limited` (subscription limits), `transient`, `timeout`, `cancelled`, `invalid_output`, `error`. Transient ones are retryable by the engine; auth and invalid output are not.
- **Resuming:** implementer sessions are persisted (`--resume <session_id>` for remediation); reviewers use `--no-session-persistence`.

### Permission model (each rule verified with real calls; see `tests/live/`)
Run `FACTORY_LIVE=1 pnpm vitest run tests/live` to re-verify against an upgraded CLI (uses a little subscription quota).
- A **deny beats a broad allow**. Path scoping uses `Edit(<glob>)`, which governs both the Edit and Write tools. (`Write(<glob>)` does not work.) Bare `Write`/`Edit` allows are what enable those tools.
- `Bash(git:*)` allowed with `Bash(git push:*)` denied permits other git commands and refuses push.
- **Never grant bare `Read`/`Grep`/`Glob`.** With no rule they are confined to the worktree; a bare allow lets an agent read any file the user can. (A live test caught this mistake; there is a regression test.) Bash built-ins such as `cat`/`ls`/`grep` are also refused outside the worktree.
- **Never grant bare `Write`/`Edit`.** They allow writing anywhere the user can (found live: an implementer wrote to `$HOME` and a sibling directory). The implementer's edit access is `Edit(//<worktree>/**)` only; verified live for the Write tool, shell redirection and `cp` (`tests/live`).
- **Path rules must be absolute.** Claude Code's shell keeps `cd` between calls and relative rules resolve against the *current* directory, so after `cd specs/x` the rule `Edit(specs/**)` silently matched nothing and the agent's in-scope edits were refused (found live: it stalled spec remediation; reproduced 4/4, and the live test `cd drift` fails without the fix). Every scoped allow and every protected-path deny is therefore emitted in relative **and** absolute (`//abs/path/...`) form, for both spellings of the root on macOS (`/var` and `/private/var` are not equated). Agents are also told never to `cd`. Protected-path denies held under drift even before this fix; they are anchored anyway.
- Profiles (`src/agents/permissions.ts`): `read-only` (reviewers/analysts/classifier and the Haiku `prompt-writer`), `spec-writer` (may only edit `specs/**` and `.specify/**`), `implementer` (edit + `git add/commit` + the project's test/lint commands; it also resolves merge conflicts, but the factory runs the fetch and the merge itself, the agent only edits files, stages and commits; denied: push, fetch, pull, checkout/switch/branch/reset, config, remote, worktree, `gh`, curl/wget/ssh/scp, sudo, `rm -rf`, publish, docker, and edits to every protected path). A role maps to exactly one profile (`src/agents/roles.ts`); there is no per-call override.
- **Independent verification** (`AgentRunner`): after every run the factory checks the worktree itself. Any change (committed, staged, modified, untracked or renamed-away) matching `protectedPaths` fails the run and records an `agent.violation` decision; a read-only agent that altered the worktree fails the same way. Correctness does not depend on Claude Code's permission system alone.

## Spec Kit (optional: `workflow.planning_mode: speckit`)
Nothing in this section applies in the default `haiku_prompt` mode, which runs no Spec Kit command and needs no `.specify/`. Verified against github/spec-kit docs and the installed CLI (`specify` 1.4.4, installed with `uv tool install specify-cli`); nothing here is invented.
- **Setup:** `specify init --here --force --integration claude --script sh --non-interactive --ignore-agent-tools`. It adds only `.claude/skills/speckit-*/` and `.specify/` (scripts, templates, memory, workflow); application code is untouched. The factory runs this itself, never an agent.
- **Flow:** `constitution` (once per project) → `specify` → `clarify` → `plan` → `tasks` → `analyze` (read-only) → `implement` → `converge`. Artefacts land in `specs/<dir>/` (`spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, `tasks.md`, `checklists/requirements.md`) plus `.specify/feature.json`.
- **Branching:** Spec Kit's branch creation is an optional `git` extension, not installed. The factory owns branches (`factory/<KEY>`); `SPECIFY_FEATURE_DIRECTORY` is pinned per ticket to `specs/<key>-<slug>` so concurrent worktrees never race on Spec Kit's number scanning.
- **Why the factory drives the skills itself instead of `specify workflow run`:** Spec Kit's own workflow steps call `claude -p` without the factory's permission profile. Each skill is run through `ClaudeCodeAgent` under the `spec-writer` profile. We do not reimplement Spec Kit: the agent is told to read and follow the repository's own `.claude/skills/speckit-<step>/SKILL.md` (skills are not auto-registered because `--setting-sources ""` ignores repo settings on purpose; verified live that this works).
- **Clarify is interactive in Spec Kit.** In an automated run the prompt tells the agent to answer its own questions from the ticket, codebase and constitution and mark each as an "agent decision" in the artefact; anything that truly needs a human goes under `## Open questions requiring a human`, which blocks the job and is posted to the tracker.
- **Protected:** agents cannot edit `.claude/**`, `.specify/scripts|templates|workflows|integrations/**`. The spec-writer may edit only `specs/**`, `.specify/memory/**`, `.specify/feature.json`, and may run Spec Kit's four helper scripts.

## Haiku prompt mode (the default)
`REQUIREMENTS_ANALYSIS` creates the job worktree, then one read-only Haiku run (`prompt-writer`, route `prompt_generation`) reads the ticket, the code, conventions and docs and returns an implementation prompt plus acceptance criteria, or `needs_clarification` with exact questions (the job blocks and the questions go to the tracker). The result is kept in the stage's recorded output; there are no files, and the specification stages are skipped. See [workflows](workflows.md#planning-modes-per-profile).

## Specification stages (`speckit` mode: how the factory uses Spec Kit)
| Stage | What happens |
|---|---|
| `DISCOVERED` / `ELIGIBILITY_CHECK` | Re-reads the live ticket; stops if it lost `factory:enabled`, gained `factory:blocked`, or moved status since discovery. |
| `REQUIREMENTS_ANALYSIS` | Creates the job worktree. Cheap advisory classification (Haiku). Claude read-only analyst answers `ready` or `needs_clarification` with exact questions; the latter blocks the job and posts them to the tracker. |
| `SPECIFICATION_GENERATION` | Writes `ticket.md`, then runs `specify → clarify → plan → tasks`. After each step the **factory** commits the artefacts (`spec(KEY): <step>`, author "Software Factory") and checkpoints it, so a crash or retry resumes at the failed step. Blocks with onboarding instructions if Spec Kit is not on the default branch. |
| `SPECIFICATION_REVIEW` | Independent review of the full artefact text by the `independent_review` route: any OpenAI-compatible endpoint (base URL, model, optional key read from an environment variable), read-only. **If no reviewer is set (the default), this stage is skipped**: it completes as a pass with no findings, records a `review.skipped` decision, and calls no model. Only if the route is an endpoint (`local`) and it is unavailable: fall back to a fresh Claude reviewer (`independentReviewFallback: claude`, recorded as `review.degraded`) or block. `blocker`/`major` findings → remediation. |
| `SPECIFICATION_REMEDIATION` | Claude spec-writer fixes valid findings and must reject invalid ones with evidence (stored as `remediation.rejected` decisions). Minor findings are not sent. |
| `SPECIFICATION_VALIDATION` | Deterministic gate calibrated on real output (files present; FR-/SC- ids; Given/When/Then; tasks; checklist complete; no `[NEEDS CLARIFICATION]` or template placeholders; no open human questions) then Spec Kit `analyze` (read-only, structured). CRITICAL/HIGH findings → remediation. |
`LOCAL_MODEL_REVIEW` (the independent code review, shown as "Independent review") follows the same rule: the `independent_review` route reviews the diff against the spec, and with no reviewer set it is skipped (`review.skipped`, no model call). The security review of security-sensitive diffs is separate (the `final_review` route) and runs either way.

Remediation is capped at `maxRemediationAttempts` (3), then `NEEDS_ATTENTION`. Note the workflow is review → remediation → validation (as specified); the reviewer does not re-review after a fix, validation and analyze re-check consistency.

## Onboarding a project (`speckit` mode only)
Not needed in `haiku_prompt` mode. `pnpm factory project:onboard <id>` creates the local branch `factory/onboard-speckit` in `<dataDir>/workspaces/<id>/_onboard-speckit`: `specify init` (committed), then an agent writes an *evidence-based* constitution from the README, CLAUDE.md, CI and tooling (committed). It never pushes, never overwrites an existing `.specify/`, and is idempotent and crash-safe. The constitution is project policy, so a human reviews and merges it (PR creation arrives in the pipeline); until then `SPECIFICATION_GENERATION` blocks with exactly this instruction.

## Linear workspace setup
`pnpm factory linear:check` (read-only) lists what is missing per bound team, split into **required** (what the factory writes today: statuses Ready for specification, Specification review, In progress, Ready for review, Merging, Done, Blocked; labels `factory:enabled`, `factory:blocked`) and **optional** (`Ready for development`, `Changes requested`, and the `factory:autonomous|bugfix|feature|maintenance` labels). `pnpm factory linear:setup` creates the missing required items as a **dry run by default**; `--apply` creates them, `--include-optional` adds the rest. It only creates (team-scoped labels, sensible state types), never edits or deletes, matches existing names case-insensitively, and is idempotent. Verified against the real `JAM` team.

## Running project commands safely
`src/exec/sandbox.ts` builds a macOS `sandbox-exec` profile: `(deny network*)` (except for `install`, which gets network, and projects that set `allowLoopback`, which get TCP to this machine only), writes only to the worktree, `/tmp` and (for installs) package caches, and `(deny file-read-data)` under `$HOME` with a short allowlist (worktree, nvm/npm/pnpm/cargo/etc. toolchain dirs, configurable via `factory.sandbox.readAllow`), with credential stores (`.ssh`, `.aws`, `.gnupg`, `.claude`, `.config/gh`, `.software-factory`, `Keychains`) denied last so no allowlist entry can re-expose them. Metadata reads stay allowed because path resolution needs them. `sandbox-exec` is deprecated by Apple but present and effective on this macOS; the sandbox is required by default (`factory.sandbox.required`).
The agent's only way to run project code is `factory-exec <test|lint|typecheck|build|install|visual>` (`src/exec/factory-exec.ts`): the job's wrapper script and spec live in `<dataDir>/jobs/<id>/` (mode 700/600, outside the worktree), the command text comes from `config/projects.yaml`, and the agent's permission rule allows only that one absolute path.
Configure per project: `commands: { install?, build?, test, lint?, typecheck?, visual? }`. `test` is mandatory for implementation.
`visual` is an optional browser check (for example `pnpm exec playwright test`). It runs like `test` (same sandbox, same check tool, after `test` in AUTOMATED_TESTING, `factory-exec visual` exits 65 when unset) and gets loopback only when the project sets `allowLoopback`, so a Playwright `webServer` on 127.0.0.1 can start. Never external network. The project supplies Playwright and its config (the factory has no Playwright dependency), and browser binaries must be installed by the project's `install` command (which has network) or a setup step, because checks cannot download them. Playwright's default output directories (`test-results/`, `playwright-report/`, `blob-report/`, `playwright/.cache/`) are never staged by the factory's commit path. With a `visual` check configured the implementer runs it and defers only what a person must judge.

### `.software-factory.yml`: settings that live with the code
A repository may carry its own factory settings in `.software-factory.yml` at its root (a mapping, or a one-element list). Accepted keys, all optional except `id`: `id`, `name`, `defaultBranch`, `github: { account, repo }`, `commands: { install, build, test, lint, typecheck, visual }`, `allowLoopback`. Anything else (for example `commands.tset`) is an error.
- **Precedence:** `projects.yaml` stays the registry (id, enabled, tracker/Linear binding, autonomy, overrides). For the fields the file sets, **the file wins**; `commands` and `github` merge key by key; fields it omits keep the `projects.yaml` value or the default. `id` must equal the project's id in `projects.yaml`.
- **Source:** only the **committed default branch** (`origin/<defaultBranch>`, else the local branch). The job worktree and uncommitted working copy are never read, so a job cannot change its own commands. A missing file changes nothing (a file that was applied and is later deleted stays applied until restart). A git failure while reading keeps the previous settings and shows an error. The file is always read from the branch `projects.yaml` names, even if the file sets a different `defaultBranch`, which must be a plain branch name.
- **GitHub account:** `github.account` and `github.repo` from the file select which credentials the factory uses and which remote it talks to, so they carry the same trust as the commands. The factory-own-repository guard checks only the local checkout path, not these values. Review changes to `github` in this file like changes to `commands`.
- **When:** after the clone is ensured (service start, Validate, Run checks), when Run checks fetches the default branch, and when the project is saved in Settings. No polling.
- **Invalid file:** none of it is applied, the previous settings stay, and the error shows on the project's onboarding steps ("`.software-factory.yml` valid"). Secret-looking keys (`apiKey`, `token`, `password`, `secret`) are rejected like in `projects.yaml`.
- **Trust:** the file is trusted like the repo's package scripts. `commands.install` runs **with network access**, and `allowLoopback: true` **loosens the sandbox** (TCP to this machine). Anyone who can merge to the default branch can set both; see [SECURITY.md](../SECURITY.md).

## GitHub delivery
(Bitbucket projects use the same delivery stages through `src/bitbucket/client.ts`: see [bitbucket](bitbucket.md).) If the PR later conflicts with its target branch, `CONFLICT_RESOLUTION` merges the target into `factory/<KEY>` and the normal push (still never forced) updates the PR: see [workflows](workflows.md).
`src/github/client.ts` wraps `gh` (JSON fields verified against gh 2.105 output on a real repo): `gh pr list/view --json number,url,state,isDraft,headRefName,headRefOid,baseRefName,mergedAt,mergeable,mergeStateStatus,reviewDecision`, `gh pr checks --json name,state,bucket,link,workflow`, `gh pr create --head --base --title --body-file`, `gh run view --log-failed`. It runs as the project's `github.account` (token in the child's environment only). Bodies go through a `0600` temp file, never the command line. **There is no merge method.** `no checks reported` is an empty list, not an error. Transient failures (network, 5xx, rate limits) retry; auth and not-found stop for a human; tokens are redacted from messages.
`src/repo/push.ts` is the only path to the remote: explicit `branch:branch` refspec, `--set-upstream`, the default branch protected by the git guard, only `factory/*` allowed, never forced.
`pnpm factory project:onboard <id> --pr` pushes the onboarding branch and opens a review PR (idempotent; never merges).
`pnpm factory project:check <id>` runs a project's install/build/typecheck/lint/test (and `visual`, if set) commands in a throwaway worktree of the default branch under the real sandbox: use it to prove commands before relying on them.
