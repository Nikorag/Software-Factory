# Configuration
Your settings are YAML files in `~/.software-factory/config/` (`~/.software-factory/profiles/<name>/config/` for another profile): `factory.yaml`, `models.yaml`, `projects.yaml`, `linear.yaml`, `workflows.yaml`. They are validated by Zod (`src/config/schema.ts`). Normally you never edit them by hand: **Settings** in the app writes them (comments preserved). A file you have not changed falls back to the shipped default in `config/`. Override the directory with `FACTORY_CONFIG_DIR`. Validate with `software-factory config:check`.

Useful keys: `factory.maxConcurrentJobs` (1-8), `factory.maxRemediationAttempts` (0-10: fix cycles per phase: specification, code review, CI), `factory.maxImplementationPasses` (1-10: implement-then-check-against-the-spec rounds, default 3), `factory.githubAccount` (this profile's default `gh` login), `factory.logRetentionDays`, and per project `overrides: { maxConcurrentJobs, maxRemediationAttempts, maxImplementationPasses, models }`. Model ids are never hardcoded; routes map a task (classification, specification, implementation, independent_review, final_review) to a provider (`local` | `anthropic`) and model string.


## workflows.yaml and the workflow library
`workflows.yaml` still sets per-stage timeouts and retry counts, and now tunes the built-in **Default Workflow** (its `feature` entry plus `defaults`; changing it gives the Default Workflow a new version, while running jobs keep their snapshot). Custom workflows, their prompts, models, gates, routes, project and label assignments, label priorities and the conflict policy live in the database and are managed in the app: see [Configurable workflows](configurable-workflows.md).
