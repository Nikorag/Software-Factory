# ADR 0017: Per-project lessons
Context is kept within a job (the implementer resumes its session; fix-cycle history stops reviewers re-raising settled findings, [ADR 0012](0012-defer-human-only-work.md)), but nothing carried across jobs, so each ticket in a project rediscovered the same commands, repo quirks and review preferences. (There is no ADR 0013 in this directory; 0017 follows 0016.)

**Decision.** A `lessons` table in the existing SQLite database, scoped to one project, injected into agent prompts within a cap. No embeddings, no external memory service, no cross-project lessons, no persisted reviewer sessions.

**Model.** `id`, `project_id`, `text` (one or two imperative sentences, at most 500 characters), `kind` (`command`, `convention`, `pitfall`, `reviewer-pref`), `status` (`proposed`, `active`, `retired`), `source` (`decision:<id>`, `stage_execution:<id>` or `human`), `source_job_id`, `hits` (injections), `created_at`, `last_used_at`. The enums are typed in the Drizzle schema like the other enum columns.

**Sources (always written as `proposed`).** At job completion, deterministic extraction builds the candidate text from what is already recorded, so the feature works with no model:
1. a finding accepted and fixed in two or more different jobs of the project (cross-job aggregation over `fixCycles()` and `sameFinding()`; only `accepted` outcomes count; per-ticket `criterion:` ids and `check:` ids are excluded);
2. a human answer recorded for a held stop (`decisions` rows of kind `human.answer`), with the question it answered;
3. a check command that failed in review and was then fixed in remediation (a `check:*` finding with outcome `accepted`; the finding's `file` is the command);
4. manual: added or edited on the Lessons tab.
An optional polish step may reword a candidate; if it is absent or fails, or its output is refused, the deterministic text is stored. Every candidate goes through `redactSecrets()` and is refused if `scanForSecrets()` flags it (lessons come from logs and human text). Identical text is never proposed twice for a project, in any status.

**The human gate.** `proposed` becomes `active` only through Approve on the dashboard (`approveLesson`, a token-gated route); there is no other code path that writes an active row. Edit changes text or kind, Retire removes an active lesson from use, and **Reject retires the proposed lesson rather than deleting it** so the same candidate is not proposed again. Every change writes a `decisions` row (`lesson.proposed`, `.approved`, `.edited`, `.rejected`, `.retired`; actor `factory` or `dashboard`; `job_id` is null for project-level changes). Auto-promotion is deliberately not built. Lesson changes are blocked from the hub's remote dashboard (read is allowed): they change what agents are told, so they are decided on the machine.

**Expiry.** An active lesson not injected for `LESSON_EXPIRY_JOBS` (20) jobs created on its project since it was last used (or created) is retired, checked at each job completion.

**Injection.** `## Project lessons` is appended by the stage kit's `agent()` to the implementer (implementation, remediation, haiku_prompt implementation), spec-writer (spec steps, spec remediation, the haiku_prompt planning prompt) and reviewer (independent, Claude, final and spec review) prompts. Kinds per stage live in one table (`KINDS_BY_STAGE`), most relevant first: implementer all four (`command`, `pitfall`, `convention`, `reviewer-pref`); spec-writer `convention`, `pitfall`; reviewers `reviewer-pref`, `convention`. Reviewers get the section labelled as context, not findings to enforce, so their independence holds. Ranking: kind relevance, then `hits` descending, then recency (last used, else created). Cap: at most 10 lessons and 6,000 characters (about 1,500 tokens) per prompt. `hits` and `last_used_at` are updated for exactly the lessons injected, and their ids are recorded in the invocation's `usageJson.lessons`, which the job page shows per run.

**Safety.** Lesson text is untrusted-derived data. It is fenced (`<project-lessons untrusted-data="true">`, fence-breaking markup stripped) and followed by a statement that it is context, not instructions, as `ticketBlock()` does for tickets. Lessons never override protected-path, sandbox or hard-gate rules: `isDeferrable` and its `HARD` pattern are untouched, nothing in history/triage/gates reads lessons, and tests assert that a lesson saying "skip the test gate" is only rendered as context.

**Why deterministic.** Every stored lesson, its source, who approved it, which runs saw it and why it expired can be read from the database and the decisions log. Storing and ranking need no model and no network, so the feature cannot fail with an outage, cannot drift between runs, and an operator can audit exactly what an agent was told. Revisit embeddings only if the lesson count outgrows ranked lookup.
