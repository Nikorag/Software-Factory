# ADR 0011: One stable entry point, tsx at runtime, and updates that stop, back up and roll back

**Decision.** Everything outside the install that runs the factory (the `software-factory` launcher, the LaunchAgent, the desktop app's "Start all profiles") calls `<app>/bin/factory` through `/bin/sh`. That script picks Node (`$FACTORY_NODE`, else the Node recorded in `node_modules/.factory-node` when dependencies were installed, else `node` on PATH, else the Homebrew locations; 22+ only) and runs `node --import tsx src/cli.ts` from the install dir. The factory always runs its TypeScript source: a compiled `dist/` is never preferred.

`update` stops every running profile and the LaunchAgent, backs up each profile's database (`VACUUM INTO`), moves the code, reinstalls dependencies, checks the native SQLite module loads (rebuilding it if needed) and rebuilds the dashboard, then re-renders the LaunchAgent and restarts what was running. A marker in the git dir records an update until it has fully installed, so it is retried rather than reported as "up to date"; a failed install rolls the code back to the last fully installed commit and reinstalls that.

**Why.** The LaunchAgent and the app used to carry `process.execPath` (a versioned nvm or Homebrew Cellar path) and a tsx path inside the pnpm store (`.pnpm/tsx@x.y.z/...`). A tsx bump or a Node switch broke them silently: a 30-second launchd restart loop, or a menu item that did nothing. A path that never changes, with the version-specific parts resolved at run time, removes that whole class of failure; the plist is still re-rendered after an update so its PATH stays current.

**Why tsx and not `dist/`.** The code finds `package.json`, the Drizzle migrations, the shipped config and `web/dist` relative to its source files; from `dist/src/...` those paths do not exist, and `update` never rebuilt `dist/` anyway. Running the source through tsx is what development, tests and the launcher already did; one runtime layout is simpler than making every path layout-independent. The cost is tsx's transpile time at startup (well under a second).

**Why stop the services.** A service left running during an update keeps old code against a database the new code may migrate, and serves a dashboard whose files are being rebuilt under it. Jobs survive a stop (their stage is redone), but redoing a long stage costs time, so `update` refuses while jobs run unless told to `--wait` or `--force`.
